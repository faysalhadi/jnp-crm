# FIX — Salesperson can reach owner-only tabs from the client detail view

Symptom: a salesperson opens a client. The owner's side navigation appears and
they can navigate into Marketing, Parts DB, Sales History, Sourcing, Traders
and Ask Claude.

Cause: nav access is currently decided separately in each nav component. The
client detail view renders a nav that never got the role gate, so the
restriction is bypassed.

The fix is NOT to add one more conditional to one more file. Access must be
decided in ONE place, and each restricted tab must also refuse to render for a
salesperson even if something manages to navigate there. Two layers.

Read every file before editing.
After all changes: npm run build, fix ESLint errors, git push.

---

## STEP 1 — Single source of truth for nav access

Create a new file: **src/constants/access.js**

```js
// Tabs a salesperson may reach. Everything else is owner-only.
export const SALESPERSON_TABS = ['home', 'customers', 'stock'];

// Side drawer / sidebar items a salesperson may reach.
export const SALESPERSON_DRAWER_ITEMS = ['settings', 'signout'];

export function canAccessTab(tabId, { isOwner, isViewingAs }) {
  if (isOwner && !isViewingAs) return true;
  return SALESPERSON_TABS.includes(tabId);
}

export function canAccessDrawerItem(itemId, { isOwner, isViewingAs }) {
  if (isOwner && !isViewingAs) return true;
  return SALESPERSON_DRAWER_ITEMS.includes(itemId);
}
```

Then create a hook in **src/context/ProfileContext.js** (add to the existing
file, export from the same place):

```js
import { canAccessTab, canAccessDrawerItem } from '../constants/access';

// inside ProfileProvider, before the return:
const access = {
  canTab: (tabId) => canAccessTab(tabId, { isOwner, isViewingAs }),
  canDrawer: (itemId) => canAccessDrawerItem(itemId, { isOwner, isViewingAs }),
};
```

Add `access` to the context value object.

Every nav component from here on uses `access.canTab(...)` /
`access.canDrawer(...)`. No component decides this on its own any more.

## STEP 2 — Apply the single check in every nav component

replace whatever ad-hoc `isOwner` / `isViewingAs` logic exists with the shared
check.

### src/components/layout/BottomNav.js
```js
const { access } = useProfile();
const visibleTabs = tabs.filter(tab => access.canTab(tab.id));
```

### src/components/layout/DesktopSidebar.js
```js
const { access } = useProfile();
// filter the tab list with access.canTab(...)
// filter the drawer-style items with access.canDrawer(...)
```

### src/components/layout/SideDrawer.js
```js
const { access } = useProfile();
// Marketing, Parts DB, Sales History each wrapped with:
{access.canDrawer('marketing') && ( ... )}
{access.canDrawer('parts') && ( ... )}
{access.canDrawer('sales_history') && ( ... )}
// Settings and Sign Out always render
```

### src/components/layout/TopBar.js

## STEP 3 — Fix the leak in the client detail view

Based on what STEP 0 found, apply the matching fix:

**If ChatDetailView renders its own nav:** remove it. The detail view should
not render navigation at all — it is a child of the main layout, which already
provides nav.

**If the detail view is a full-screen overlay and nav is showing through:**
give the overlay a solid background and a high enough z-index that the
sidebar is genuinely covered, and make sure the sidebar is not rendered on top
of it.

**If the layout renders the sidebar unconditionally:** that is fine now,
because STEP 2 makes the sidebar itself role-aware. Verify by reading
DesktopSidebar and SideDrawer that no item escapes `access`.

Whichever case applies, the detail view must have a working back button that
returns to the Clients list.

## STEP 4 — Second layer: tabs refuse to render

Nav filtering is not enough on its own. If a tab id ever gets set some other
way — a stale state value, a deep link, a stray `setActiveTab` call — the
restricted tab would still render. Close that.

### src/App.js

Read the file. Find where the active tab is rendered (the switch or map that
picks which tab component to show).

Wrap it with the access check:

```js
const { access, profileLoading } = useProfile();

// Never render a tab this user may not access.
const safeTab = access.canTab(activeTab) ? activeTab : 'home';
```

Then render based on `safeTab`, not `activeTab`.

Also add a correcting effect so the nav highlight does not sit on a tab that is
not being shown:

```js
useEffect(() => {
  if (!profileLoading && !access.canTab(activeTab)) {
    setActiveTab('home');
  }
}, [profileLoading, activeTab, access]);
```

Note: `access` is recreated each render. To avoid an infinite loop, either
wrap `access` in `useMemo` inside ProfileContext (dependencies: `isOwner`,
`isViewingAs`), or depend on `isOwner, isViewingAs, activeTab` in the effect
instead of `access`. Do the useMemo — it is cleaner:

```js
// in ProfileContext:
const access = useMemo(() => ({
  canTab: (tabId) => canAccessTab(tabId, { isOwner, isViewingAs }),
  canDrawer: (itemId) => canAccessDrawerItem(itemId, { isOwner, isViewingAs }),
}), [isOwner, isViewingAs]);
```

### Guard the owner-only tab components themselves

At the top of each of these components, return null (or a short message) if
the user should not be there. This is cheap and makes the restriction
impossible to bypass from the UI:

- src/components/tabs/MarketingTab.js
- src/components/tabs/PartsCompatibilityTab.js
- src/components/tabs/SalesTab.js
- src/components/tabs/AskClaudeTab.js
- src/components/tabs/TradersTab.js
- src/SourcingModule.js

```js
const { isOwner, isViewingAs } = useProfile();
if (!isOwner || isViewingAs) return null;
```
