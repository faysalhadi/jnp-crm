JNP CRM — The Fork + Soft Hold on Stock

WHY
A customer asks about a laptop. It goes one of two ways: we have it (blocked
on him deciding) or we don't (blocked on supply). Today that fork happens only
in the agent's head and the app never learns which side it landed on.

There are now FOUR people using this app. The failure this prevents: Ahmed
quotes unit #47 to Rehman, Bilal quotes the same unit to Ali, both promise it,
one of them loses face with a client.

Read every file fully before editing. Targeted edits only — do NOT rewrite
whole files. Run `npm run build` at the end and fix all ESLint errors.

-- minimal identity: a hold has to be able to name a person
CREATE TABLE IF NOT EXISTS profiles (
  id         uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  full_name  text,
  role       text DEFAULT 'salesperson'
             CHECK (role IN ('owner','manager','salesperson')),
  active     boolean DEFAULT true,
  created_at timestamptz DEFAULT now()
);
ALTER TABLE profiles DISABLE ROW LEVEL SECURITY;

-- soft hold on a stock unit
ALTER TABLE stock ADD COLUMN IF NOT EXISTS quoted_by      uuid;

STEP 1 — NEW FILE: src/utils/holds.js
════════════════════════════════════════════════════════════════════════

Pure helpers. No React, no supabase.

  export const HOLD_HOURS = 48;

  export function isHoldActive(stockItem)
    true when status === 'quoted' AND quoted_at is set
    AND (now - quoted_at) < HOLD_HOURS.
    Returns false safely for null/missing input.

  export function holdRemainingMs(stockItem)
    Milliseconds left, or 0 if not held / expired.

  export function formatHoldRemaining(stockItem)
    "31h left" · "4h left" · "42m left" · "" when not held.

  export function effectiveStatus(stockItem)
    Returns the status to ACT on:
      'quoted' whose hold has expired  →  'available'
      everything else                  →  the stored status
    Every availability check in the app must go through this.

DESIGN RULE — IMPORTANT:
Expiry is COMPUTED, never stored. There is no scheduled job and no cron.
A hold older than HOLD_HOURS is simply treated as available everywhere.
Do NOT write a background task or timer to flip statuses.

Optionally, when the app loads stock and finds expired 'quoted' rows, it may
lazily clear them (status back to 'available', quoted_* to null) as a tidy-up.
That is a convenience only — correctness must never depend on it.

STEP 2 — NEW FILE: src/services/stockHoldService.js
════════════════════════════════════════════════════════════════════════

  import { supabase } from "../supabase";

  export async function placeHold(stockId, { customerId, dealId })
    Reads the row first. If isHoldActive() and quoted_by is a DIFFERENT user,
    return { ok:false, conflict:true, heldBy, heldUntil } — do NOT overwrite.
    Otherwise set:
      status='quoted', quoted_by=<current user id>, quoted_to=customerId,
      quoted_at=now(), quoted_deal_id=dealId

  export async function releaseHold(stockId)
    status back to 'available', quoted_* all null.
    Only if the row is not already 'sold' or 'reserved'.

  export async function upgradeToReserved(stockId)
    status='reserved', keep quoted_to and quoted_deal_id, clear quoted_at
    so no countdown shows on a hard hold.

  export async function getHolderName(userId)
    Looks up profiles.full_name. Falls back to "another agent" when the
    profiles row is missing. Cache results in a module-level Map — this is
    called per stock row and must not fire a query each time.

Current user id: use the existing AuthContext if it exposes one; otherwise
supabase.auth.getUser(). Do NOT add a new auth mechanism.

Every function returns { ok:true, ... } or { ok:false, error }. Never throws.

STEP 6 — RELEASE AND UPGRADE
════════════════════════════════════════════════════════════════════════

  · deal → confirmed_pending_pickup   →  upgradeToReserved(stockId)
  · deal → lost                       →  releaseHold(stockId)
  · deal → watching / parked          →  releaseHold(stockId)
  · deal → closed                     →  leave it; the existing sold flow owns it
  · stock_item_id changed on a deal   →  release the old unit, hold the new one

Hook these into wherever deal stage changes are already handled. Do not build
a new stage-change mechanism.
