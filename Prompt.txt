# FIX 3 SALESPERSON BUGS

Three bugs in the salesperson role system. Read every file before editing.
After all changes: npm run build, fix ESLint errors, git push.

---

## BUG 1 — Salesperson sees the OWNER's data on first load

Symptom: logging in as a salesperson, the Home tab first shows the owner's
overdue follow-ups / tasks. Clicking a client then going back to Home fixes it.

Cause: data fetching starts BEFORE the profile has loaded. At that moment
`isSalesperson` is false and `currentProfile` is null, so no `assigned_to`
filter is applied and the query returns everyone's data. When the profile
finishes loading a re-render happens, but some already-fetched state is never
cleared until navigation forces a re-fetch.

### 1a. src/context/ProfileContext.js

Make sure the provider exposes a loading flag. Read the file — if there is no
`profileLoading` state, add it:

```js
const [profileLoading, setProfileLoading] = useState(true);
```

Set it to `true` at the start of the profile fetch and `false` in a `finally`
block (both on success and on error). Export `profileLoading` in the context
value.

### 1b. src/context/CustomerContext.js — gate the fetch

Read the file. Find the useEffect that triggers the customers fetch.

Pull `profileLoading` out of `useProfile()` and refuse to fetch until the
profile is known:

```js
const {
  isOwner, isSalesperson, currentProfile,
  viewingAs, isViewingAs, profileLoading,
} = useProfile();
```

At the very top of the fetch function:

```js
async function fetchCustomers() {
  // Do not fetch until we know who the user is — otherwise the
  // assigned_to filter is missing and we leak the owner's data.
  if (profileLoading) return;
  if (!currentProfile?.id) return;

  setLoading(true);
  ...
}
```

And add `profileLoading` to the useEffect dependency array alongside
`currentProfile`, `isSalesperson`, `viewingAs`:

```js
useEffect(() => {
  fetchCustomers();
}, [profileLoading, currentProfile?.id, isSalesperson, viewingAs?.id]);
```

Also: when `profileLoading` is true, `loading` in CustomerContext should be
`true` (not false with an empty/stale list). Initialise `const [loading,
setLoading] = useState(true);` if it isn't already.

### 1c. src/components/tabs/HomeTab.js — scope ALL derived data

Read the file carefully. HomeTab builds the morning brief, follow-ups, alerts,
re-engage and waiting-matches sections.

Check every data source in this file:

- If HomeTab queries Supabase directly (e.g. `supabase.from('follow_ups')`,
  `supabase.from('deals')`, `supabase.from('activity_log')`), those queries are
  NOT role-filtered. That is the real leak.
- Fix: derive everything from the customers already in `CustomerContext`
  (which IS filtered), not from unfiltered direct queries.

Concretely, for any direct query in HomeTab, add a customer-id restriction:

```js
const { customers, loading: customersLoading } = useCustomers();

// ids of customers this user is actually allowed to see
const visibleIds = useMemo(() => customers.map(c => c.id), [customers]);

// then every direct query gets:
//   .in('customer_id', visibleIds)
// and must not run while visibleIds is empty + still loading
```

Guard the whole fetch:

```js
useEffect(() => {
  if (customersLoading) return;
  if (!visibleIds.length) {
    setFollowUps([]);
    setAlerts([]);
    return;
  }
  loadHomeData();
}, [customersLoading, visibleIds.join(',')]);
```

Note: `.in('customer_id', [])` with an empty array returns nothing in Supabase,
which is correct — but make sure the code does not skip the filter entirely
when the array is empty.

### 1d. Show a loading state instead of stale data

In HomeTab, while `profileLoading || customersLoading` is true, render a
spinner instead of the sections. This prevents the flash of owner data.

```js
const { profileLoading } = useProfile();
if (profileLoading || customersLoading) {
  return <Spinner />;  // use the existing src/components/ui/Spinner.js
}
```

## BUG 2 — Client saved by a salesperson is assigned to the OWNER

Symptom: salesperson adds a client, the client does not appear in their list —
it appears in the owner's list instead (unassigned).

Cause: the customer INSERT never sets `assigned_to`, so it lands as NULL and is
only visible to the owner.

### 2a. src/ContactModal.js

Read the file. Find the Supabase insert into `customers`.

Import the profile context:

```js
import { useProfile } from './context/ProfileContext';
// (check the actual relative path from src/ContactModal.js)

const { currentProfile, isSalesperson } = useProfile();
```

Add `assigned_to` to the inserted row:

```js
const payload = {
  name,
  number,
  contact_type: contactType,
  tags,
  // ...existing fields...

  // A salesperson always owns the clients they create.
  // The owner creates unassigned clients (assigned_to stays null)
  // and assigns them later from the client header.
  assigned_to: isSalesperson ? currentProfile?.id : null,
};
```

Do NOT set assigned_to when the owner is in `viewingAs` mode — that mode is
read-only and ContactModal should not even be reachable there.

### 2b. src/context/CustomerContext.js — any other create path

Search the file for `.insert(` on the `customers` table (there may be an
`addCustomer` / `createCustomer` helper, and possibly a walk-in or quick-add
path). Apply the same `assigned_to` rule to every one of them.

Also search the whole codebase for other customer inserts:

```bash
grep -rn "from('customers')" src/ | grep -i insert
```

Fix each hit the same way.

### 2c. Any other insert path that needs it

Check these files for customer creation and apply the same rule if found:
- src/components/modals/QuickSaleModal.js  (walk-in creation)
- src/hooks/useChatActions.js
- src/components/tabs/CustomersTab.js

## BUG 3 — "Open chat" on a newly saved client shows nothing

Symptom: salesperson saves a client, taps open chat, the chat view is empty.

Cause: two things, both downstream of Bug 2.
1. The new customer has `assigned_to = null`, so after the refetch it is
   filtered OUT of the salesperson's `customers` array. The chat view looks the
   customer up by id in that array, finds nothing, and renders blank.
2. Even with 2a fixed, the local state may not include the new row before the
   navigation happens.

### 3a. Return the inserted row and add it to local state

In whichever function does the insert (ContactModal.js and/or
CustomerContext), use `.select().single()` so the created row comes back, then
push it into the customers array immediately:

```js
const { data, error } = await supabase
  .from('customers')
  .insert(payload)
  .select()
  .single();

if (error) throw error;

// optimistic — the row is already correctly scoped because
// assigned_to was set at insert time
setCustomers(prev => [data, ...prev]);

return data;   // the caller needs the id to open the chat
```

Make sure `assigned_to` is in the `.select()` field list wherever customers are
selected (including the main fetch query) — otherwise the filter logic
downstream has nothing to compare against.

### 3b. Navigate using the returned row, not a stale lookup

Find where "open chat" happens after saving. It probably does something like
`setSelectedCustomer(someId)` and then the chat view looks the id up in the
customers array.

Change it to pass the returned customer object directly:

```js
const created = await addCustomer(payload);
if (created) {
  setSelectedCustomer(created);   // the full object, not just an id
  setActiveTab('customers');
}
```

If `selectedCustomer` is stored as an id elsewhere in the codebase, keep that
shape but make sure the array update in 3a has already run before navigating
(await it).

### 3c. Defensive guard in ChatDetailView

Read src/components/chat/ChatDetailView.js. If the customer lookup returns
undefined, it currently renders blank. Add an explicit fallback so this failure
mode is visible rather than silent:

```js
if (!customer) {
  return (
    <div style={{
      padding: 32, textAlign: 'center',
      color: '#7880A3', fontSize: 13,
    }}>
      Client not found. Go back and try again.
    </div>
  );
}
```

## SQL — fix the clients already created wrong

Run this in the Supabase SQL Editor AFTER deploying, to check for orphans:

```sql
-- see unassigned clients created recently
SELECT id, name, number, created_at, assigned_to
FROM customers
WHERE assigned_to IS NULL
ORDER BY created_at DESC
LIMIT 50;
```

Then assign the ones that belong to a salesperson (replace both UUIDs):

```sql
UPDATE customers
SET assigned_to = '<salesperson-profile-uuid>'
WHERE id IN ('<customer-uuid-1>', '<customer-uuid-2>');
```

Get the salesperson UUID with:

```sql
SELECT id, name, role FROM profiles;
```
